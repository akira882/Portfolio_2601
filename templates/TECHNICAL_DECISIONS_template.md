# Technical Decisions - ClearTask Web版

**技術選定理由と設計判断の記録**

このドキュメントでは、ClearTask開発における主要な技術選定の理由と、
採用責任者に対して「なぜこの技術を選んだのか」を論理的に説明します。

---

## 🎯 技術選定の基準

プロジェクトの技術選定において、以下の基準を重視しました：

1. **開発速度** - 限られた時間でMVPを実現
2. **スケーラビリティ** - 将来的なユーザー増加に対応
3. **コスト** - 開発・運用コストの最小化
4. **学習コスト** - 新規技術習得の負担
5. **保守性** - 長期的なメンテナンス性

---

## 📊 技術スタック選定

### **1. フロントエンド: HTML/CSS/JavaScript + TypeScript**

#### **選定理由**

| 項目 | 評価 | 理由 |
|------|------|------|
| 開発速度 | ⭐⭐⭐⭐ | フレームワーク不要、即座に開発開始可能 |
| 学習コスト | ⭐⭐⭐⭐⭐ | 基本的なWeb技術のみで実装可能 |
| パフォーマンス | ⭐⭐⭐⭐ | フレームワークのオーバーヘッドなし |
| 保守性 | ⭐⭐⭐ | TypeScript導入で型安全性確保 |

#### **代替案との比較**

| 技術 | メリット | デメリット | 選定結果 |
|------|----------|-----------|---------|
| **Vanilla JS + TS** | 軽量、学習コスト低 | 大規模化に弱い | ✅ **採用** |
| React | コンポーネント化、再利用性 | 学習コスト高、オーバーヘッド | ❌ 不採用 |
| Vue.js | 学習曲線が緩やか | 依存関係増加 | ❌ 不採用 |

#### **TypeScript導入判断**

**部分的にTypeScript採用（34.0%）**:
- **採用箇所**: 型定義（`src/types/`）、重要なビジネスロジック
- **理由**:
  - ✅ 型安全性によるバグ防止
  - ✅ IDE補完で開発効率向上
  - ✅ 既存JavaScriptとの共存が容易
  - ❌ 完全TypeScript化は学習コスト高

**結論**: 段階的TypeScript導入で、型安全性と開発速度のバランスを実現

---

### **2. バックエンド: Firebase**

#### **選定理由**

**Firebase Authentication + Cloud Firestore**を採用した理由：

1. **開発速度の圧倒的優位性**
   - バックエンドサーバー実装不要
   - 認証機能が数行のコードで実装可能
   - リアルタイム同期が標準機能

2. **コスト最適化**
   - 無料枠が充実（Spark Plan）
   - サーバー管理コスト不要
   - スケールアップ時も従量課金

3. **スケーラビリティ**
   - Google Cloud基盤で高可用性
   - 自動スケーリング
   - グローバル展開が容易

#### **代替案との比較**

| 技術 | 初期コスト | 運用コスト | 開発速度 | スケーラビリティ | 選定結果 |
|------|-----------|-----------|---------|----------------|---------|
| **Firebase** | ¥0 | 従量課金 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ✅ **採用** |
| Node.js + MongoDB | サーバー代 | 月額数千円 | ⭐⭐⭐ | ⭐⭐⭐ | ❌ 不採用 |
| Supabase | ¥0 | 従量課金 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | △ 候補 |
| AWS Amplify | ¥0 | 従量課金 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | △ 候補 |

**Firebaseを選んだ決定的理由**:
- ✅ 公式ドキュメントが充実
- ✅ 学習リソースが豊富（日本語も多い）
- ✅ Firebase Hostingとの統合が容易
- ✅ 実務で広く使われている（履歴書に書きやすい）

## 🏗️ アーキテクチャ設計判断

### **1. NoSQL (Firestore) vs SQL (PostgreSQL)**

#### **Firestoreを選んだ理由**

**タスク管理アプリの特性**:
- タスクデータは独立したドキュメント
- 複雑なリレーションシップ不要
- リアルタイム同期が重要

**比較表**:

| 要件 | Firestore | PostgreSQL |
|------|-----------|-----------|
| リアルタイム同期 | ✅ 標準機能 | ❌ 自前実装必要 |
| スケーラビリティ | ✅ 自動 | △ 手動調整 |
| クエリ柔軟性 | △ 制限あり | ✅ SQL全機能 |
| トランザクション | ✅ あり | ✅ あり |

**結論**: タスク管理の要件ではFirestoreの利点が大きい

---

### **2. 優先度自動計算アルゴリズム**

#### **アイゼンハワーマトリクスベースの計算式**

```
優先度スコア = 重要度 × 3 + 緊急度
```

#### **なぜ重要度を3倍重視するのか**

**根拠**:
- アイゼンハワーマトリクスの原則：「重要だが緊急でないタスク」を優先すべき
- 認知障害者は「緊急だが重要でないタスク」に流されやすい
- 重要度3倍により、長期的な目標達成をサポート

**代替案との比較**:

| 計算式 | 特徴 | 欠点 | 選定結果 |
|--------|------|------|---------|
| `importance × 3 + urgency` | 重要度重視 | - | ✅ **採用** |
| `importance + urgency` | 平等評価 | 緊急タスクに流される | ❌ 不採用 |
| `importance × urgency` | 両方高いもの優先 | 片方低いと無視される | ❌ 不採用 |

**実装例**:

```javascript
// src/utils/priorityCalc.js
export function calculatePriority(importance, urgency) {
  // importance: 1-5
  // urgency: 1-5
  // result: 1-20
  return importance * 3 + urgency;
}
```

### **3. 認証方式: Google/メール認証**

#### **Google認証を優先した理由**

**ユーザー体験の観点**:
- ✅ ワンクリックログイン（認知負荷最小）
- ✅ パスワード管理不要
- ✅ 信頼性が高い

**セキュリティの観点**:
- ✅ Googleのセキュリティ基盤を活用
- ✅ 2段階認証が自動適用
- ✅ パスワード漏洩リスクなし

**代替案**:

| 認証方式 | UX | セキュリティ | 実装コスト | 選定結果 |
|---------|-------|------------|-----------|---------|
| **Google** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ✅ **主力** |
| Email/Password | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ | ✅ **サブ** |
| 電話番号SMS | ⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐ | ❌ 不採用 |
| GitHub OAuth | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ | △ 将来検討 |

**結論**: Google認証をメインに、メール認証をフォールバックとして提供

## 🔐 セキュリティ設計判断

### **1. XSS対策: サニタイズ vs CSP**

#### **採用した対策**

**サニタイズ関数による入力値検証**:

```javascript
function sanitizeInput(input) {
  return input
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#x27;')
    .replace(/\//g, '&#x2F;');
}
```

#### **なぜCSPを実装しなかったか**

| 対策 | メリット | デメリット | 選定結果 |
|------|----------|-----------|---------|
| **サニタイズ** | 実装容易、即効性 | 漏れのリスク | ✅ **採用** |
| CSP | 包括的防御 | 設定複雑、互換性問題 | △ **将来実装** |

**段階的セキュリティ強化計画**:
1. ✅ **Phase 1**: サニタイズ実装（現在）
2. ⏳ **Phase 2**: CSP導入（次バージョン）
3. ⏳ **Phase 3**: セキュリティ監査（将来）

## ♿ アクセシビリティ設計判断

### **WCAG 2.1 AAレベルを目標とした理由**

#### **レベル比較**

| レベル | 要件 | 対応コスト | 対象ユーザー | 選定結果 |
|-------|------|-----------|-------------|---------|
| **AA** | 中程度 | 中 | 大多数のユーザー | ✅ **採用** |
| AAA | 厳格 | 高 | 全ユーザー | △ 理想 |
| A | 最低限 | 低 | 一部ユーザー | ❌ 不十分 |

#### **実装した対策**

1. **カラーコントラスト 4.5:1以上**
   ```css
   /* 背景: #FFFFFF (白) */
   /* テキスト: #333333 (濃いグレー) */
   /* コントラスト比: 12.63:1 ✅ AA合格 */
   ```

2. **キーボード操作対応**
   - Tab順序の最適化
   - Enter/Spaceでの操作可能

3. **ARIA属性の適切な使用**
   ```html
   <button aria-label="タスクを追加" role="button">
     追加
   </button>
   ```

## 📊 パフォーマンス設計判断

### **1. リアルタイム同期 vs ポーリング**

#### **Firestore onSnapshotを選んだ理由**

| 方式 | リアルタイム性 | サーバー負荷 | コスト | 選定結果 |
|------|--------------|-------------|--------|---------|
| **onSnapshot** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 読取回数課金 | ✅ **採用** |
| ポーリング (5秒) | ⭐⭐⭐ | ⭐⭐ | 高コスト | ❌ 不採用 |
| 手動更新 | ⭐ | ⭐⭐⭐⭐⭐ | 低コスト | ❌ UX悪い |

**実装例**:
```javascript
onSnapshot(collection(db, 'tasks'), (snapshot) => {
  // リアルタイムでUIを更新
  updateTaskList(snapshot.docs);
});
```

## 📚 学んだこと

### **技術選定から得た教訓**

1. **「完璧」より「完成」を優先**
   - TypeScript完全移行は時期尚早と判断
   - 段階的導入で開発速度とコード品質を両立

2. **フレームワークは必須ではない**
   - 小規模アプリではVanilla JSでも十分
   - 過剰な抽象化は認知負荷を増やす

3. **Firebaseの威力**
   - バックエンド開発不要で開発速度10倍
   - 実務レベルのアプリを数日で実装可能

4. **セキュリティは後回しにしない**
   - XSS対策、Firestoreルールは最初から実装
   - 後から追加すると大規模な修正が必要
